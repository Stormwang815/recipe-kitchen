# 接口与同步

状态：接口草案；路径不代表已部署服务。

## 约定

API 前缀 /v1；JSON；认证方式由平台选型决定。列表使用游标分页。写操作支持 Idempotency-Key；更新携带 expected_version。服务端事务内检查版本和权限，返回最新 version。

统一错误结构：{code, message, request_id, details}。建议状态码：400 输入错误、401 未登录、403 无权限、404 资源不存在或不可披露、409 版本冲突、422 业务规则不满足、429 请求过多。details 不泄露他人资源。

## 主要接口

| 方法与路径 | 作用 |
|---|---|
| POST /recipes；GET /recipes | 创建、按空间搜索菜谱 |
| GET/PATCH/DELETE /recipes/{id} | 读取、修改、软删除 |
| POST /recipes/{id}/copy-to-kitchen | 生成厨房副本，明确目标厨房 |
| POST /media/upload-intents | 申请受限上传位置，完成后校验媒体 |
| POST /imports；GET /imports/{id} | 创建及查看整理任务 |
| POST /imports/{id}/confirm | 确认草稿并保存菜谱 |
| POST /kitchens；GET /kitchens | 创建、列出已加入厨房 |
| POST /kitchens/{id}/invitations | 创建邀请，不接受客户端自设 owner 角色 |
| POST /invitations/accept | 接受邀请令牌，原子检查有效期与次数 |
| PATCH/DELETE /kitchens/{id}/members/{user_id} | 管理角色或移除成员 |
| POST /kitchens/{id}/leave | 成员退出；所有者先转移所有权 |
| GET/POST /meal-plans | 区间查询、新建排餐 |
| PATCH/DELETE /meal-plans/{id} | 修改、删除排餐 |
| POST /shopping-lists/preview | 生成需求预览，不修改正式清单 |
| POST /shopping-lists | 根据预览及用户核对创建清单 |
| GET /shopping-lists/{id} | 读取清单及来源 |
| POST /shopping-lists/{id}/refresh-preview | 对比最新菜单，返回差异 |
| POST /shopping-lists/{id}/apply-refresh | 确认应用差异，校验版本 |
| PATCH /shopping-items/{id} | 改数量、认领、标记已买；独立字段更新 |
| POST /recipes/{id}/notes | 添加个人或家庭备注 |
| POST /entities/{type}/{id}/restore | 在权限与保留期内恢复 |

## 并发与同步

首版共享编辑必须联网；本地缓存用于读取。恢复网络后按需获取最新版本，不自动提交过期的共享写入。个人本地草稿与服务器对象显式区分。

两个成员同时修改同一对象时，第一个写入成功，第二个得到 409 和最新版本。客户端展示冲突内容，允许重新应用；不对菜谱步骤采用静默最后写入覆盖。购买状态按采购项独立更新，客户端收到冲突后刷新再确认。

清单刷新采用预览版本、菜单指纹、清单版本共同校验。预览后菜单再次变化时，拒绝应用过期结果并重新预览。

可先通过页面进入、写入完成及手动刷新获取变化，实时推送作为体验增强。数据库与权限正确性不依赖推送。

## 示例

PATCH /shopping-items/{id} 请求：

```json
{"expected_version": 3, "purchased": true}
```

服务端从当前身份确定 purchased_by，不接受客户端冒充他人；响应包含新版本和最终购买状态。重复相同幂等键返回同一结果。

## 微信云开发适配

若采用云开发，首版由 wx.cloud.callFunction 承载上述业务契约，不要求先建 REST 网关。输入使用 action、payload、expectedVersion 与 idempotencyKey；HTTP 状态语义映射成业务错误码，例如 VERSION_CONFLICT。完整规则见 [技术总方案](技术总方案.md)。
