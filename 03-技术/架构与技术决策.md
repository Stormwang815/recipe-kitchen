# 架构与技术决策

状态：候选设计；未验证任何特定框架版本或平台能力。

## 分层

客户端负责页面、本地存储、跟做及计时；服务端负责身份、厨房权限、共享数据及同步；媒体存储负责私有视频和图片；后台任务负责耗时的转写与结构化提取。

建议开始使用模块化单体服务，不提前拆微服务。模块包括身份与厨房、菜谱与媒体、日历、采购、导入任务、审计。

## 候选技术路线

| 路线 | 使用时机 | 必须验证 |
|---|---|---|
| 浏览器原型 | 最快验证完整交互 | 本地数据持久性、文件处理、移动端使用体验 |
| 小程序 | 偏微信内分享和轻量访问 | 视频选择限制、媒体处理、通知、离线及分享能力 |
| 跨平台 App | 重视离线、本地媒体与系统能力 | 两端权限、后台行为、发布与维护成本 |

选择前做短期技术验证。不把浏览器原型等同于最终 App。

## 可用于估算的默认方案

流程原型可采用 TypeScript + React；浏览器本地数据用 IndexedDB。若选择 App，再评估 React Native 或 Flutter，并使用适配平台的本地数据库。联网服务可考虑 TypeScript 服务端、PostgreSQL 和私有对象存储。

以上仅作为候选，不锁定版本、不宣称兼容性已测试。落地时需要查阅对应官方文档并记录版本与验证结果。

## 本地与联网边界

个人本地原型不需要账户。联网版本引入账号后，先询问用户哪些本地菜谱需要上传；不可自动上传所有私人内容。共享内容以服务端为准，本机保留缓存。媒体只存引用，不把大视频写进数据库或日志。

计时状态记录绝对截止时间而不是依赖每秒回调。应用恢复时根据当前时间计算剩余时长。通知采用平台能力，无法保证的后台行为必须如实展示。

## 决策记录

- ADR-001：结构化菜谱为核心，来源视频为辅助。状态：建议采纳。
- ADR-002：平台导入可失败，手动创建始终可用。状态：建议采纳。
- ADR-003：首个联网版本使用服务端鉴权，不依赖客户端隐藏按钮。状态：建议采纳。
- ADR-004：首版共享修改要求在线；离线允许浏览缓存，个人本地编辑不受影响。状态：建议采纳。
- ADR-005：不做精确库存自动扣减，以每次采购前核对为准。状态：建议采纳。
